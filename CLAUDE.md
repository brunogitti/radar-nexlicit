# Radar NexLicit

Aplicação Python que captura editais com proposta em aberto no PNCP (Portal Nacional de Contratações Públicas) para 143 municípios de SP/MG/MS, filtra por palavra-chave configurável, tagueia por segmento de produto, deduplica via SQLite local, entrega por e-mail, automatiza via GitHub Actions, e expõe um painel público em Streamlit. Serve dois propósitos: uso operacional real pela NexLicit (consultoria em licitações) e peça de portfólio pública no GitHub.

Bruno (dono do projeto) é iniciante em programação e fundador da NexLicit. Prefere entender cada mudança, não só recebê-la pronta.

## Regras de colaboração (sempre valem, não são negociáveis por tarefa)

- Explicar cada mudança de código em linguagem simples antes ou durante a aplicação, assumindo zero bagagem de programação (decorators, list comprehensions, context managers, o que for, sempre explicar quando aparecer).
- Entregar uma coisa por vez (um arquivo ou uma função), esperar o Bruno rodar e confirmar entendimento antes de continuar.
- Perguntar quando faltar informação, nunca inventar ou assumir.
- Código simples e legível em vez de compacto/esperto ("sem código mágico").
- Identificadores de código (funções, variáveis, campos de banco/dataclass) em português, inclusive termos do domínio (numero_controle_pncp, orgao, municipio, banco, captura, entrega). Comentários e docstrings também em português.
- Nunca alucinar comportamento de API ou biblioteca: confirmar com documentação real ou chamada de teste real antes de afirmar algo. Já aconteceu de verdade neste projeto (situacaoCompraId vindo como número e não string; endpoint de itens/arquivos não documentado no Swagger oficial, só existe testando; limite do AppTest do Streamlit pra simular clique).
- Trabalhar por camada/etapa, não começar a próxima sem aprovação explícita.
- Nunca usar travessão (em-dash) em nenhum texto escrito pro Bruno (commits, mensagens, README): usar ponto ou vírgula.

## Convenções de teste

- `pytest`, um arquivo `tests/test_<modulo>.py` por módulo de `captura/`, `entrega/`.
- Helper `_<coisa>_de_teste()` local a cada arquivo de teste (ex. `_edital_de_teste()` em `test_banco.py`), não um módulo de fixtures compartilhado.
- Chamada externa real (HTTP, SMTP) sempre trocada por mock via `monkeypatch`, nunca bate em serviço de verdade dentro de um teste automatizado.
- Rodar tudo: `python -m pytest tests/ -v` (venv ativado). Suíte inteira roda em menos de 1 segundo, sempre rodar depois de qualquer mudança em `captura/`, `entrega/` ou `tests/`.
- Todo módulo em `captura/*.py` deveria ter teste. `pncp_client.py` ficou sem teste até ser mexido pela segunda vez (Tarefa A.2): se criar/alterar uma função ali, aproveitar pra cobrir com teste também, não só a parte nova.
- Scripts em `scripts/` (auxiliares, rodados sob demanda) e `main.py`/`painel/app.py` (orquestração) não seguem essa convenção de teste unitário; verificação deles é manual, contra dado real.

## Arquitetura, decisões não óbvias

- **`cnpj_orgao`/`ano_compra`/`sequencial_compra` não são colunas do banco** (só existem no objeto `Edital` em memória durante a captura). Qualquer coisa que precise deles depois de salvo (scripts de backfill, busca de documentos no painel) extrai de dentro do `link_pncp` já salvo, formato `.../editais/{cnpj}/{ano}/{sequencial}`, via `pncp_client.extrair_cnpj_ano_sequencial`.
- **Convenção `None` vs lista vazia** em campos tipo `beneficios_itens`, `itens`, documentos buscados ao vivo no painel: `None` significa "não foi possível buscar agora" (falha de rede/API), lista vazia significa "buscou com sucesso, não tem nada mesmo". Nunca confundir os dois na exibição.
- **Branch `data` no GitHub é a única fonte de persistência do `dados/radar.db`** entre execuções da captura automática, e é dela (não da `master`) que o Streamlit Community Cloud lê pra alimentar o painel público. Ela é reconstruída do zero a cada execução do workflow (código atual da `master` + banco atualizado, um commit só, `--force`, sem acumular histórico). Mudança em `master` só aparece no painel público depois que o workflow "Captura diaria" rodar de novo (disparado às 7h07/13h07 de Brasília por um agendador externo gratuito, mais o workflow `agendador.yml` de 2 em 2 horas com trava de 5 h como rede de segurança, ou manual via `gh workflow run captura-diaria.yml`; a "Captura diaria" não tem mais `schedule` próprio porque o do GitHub atrasava 5 a 10 horas, ver `docs/operacao-agendamento.md`).
- **O workflow é blindado contra perda do banco** (Fase 0.5, detalhes e como restaurar em `docs/operacao-banco.md`). Restaurar e publicar o banco são dois scripts em shell, `.github/scripts/restaurar_banco.sh` e `publicar_banco.sh`, e não ficam em `scripts/` porque fazem parte do fluxo diário. Regras: falha de rede ao restaurar nunca apaga nem recomeça do zero (o job falha); começar do zero só se `data` e `backups` não existirem **e** o input manual `permitir_inicio_do_zero` estiver ligado; antes de publicar confere integridade, banco não vazio e contagem de editais maior ou igual à da `data` (válvula `permitir_reducao_do_banco`, que nunca libera banco vazio); antes de sobrescrever guarda um backup `radar-AAAAMMDD-HHMMSS.db.gz` na branch `backups` (7 mais recentes, um commit só); push de `backups` e de `data` tentam de novo com espera de 10, 30 e 60 s; `concurrency` impede duas execuções ao mesmo tempo. A lógica de conferência mora em `captura/banco.py` (`verificar_integridade`, `contar_editais`, `decidir_se_pode_publicar`) e é testada com pytest; os scripts em shell foram testados em 8 cenários simulados com repositórios de brinquedo.
- **Prazo em horário de Brasília e edital excluído** (Fase 1, detalhes em `docs/decisoes.md` seção 5): tudo que compara com o prazo ou conta dias usa `captura/relogio.py`, nunca `datetime.now()` (os carimbos `visto_em`/`atualizado_em` são a exceção, ficam no relógio de onde rodou). A coluna `editais.excluido_em` marca edital que o PNCP excluiu (410), nunca se apaga linha. A captura completa chama `main.reconciliar_editais_sumidos` e a situação de edital suspenso, revogado ou anulado vem do texto da API.
- **E-mail semanal "Radar ativo" e tabela `execucoes`** (Fase 1, `docs/decisoes.md` seção 6): `entrega/batimento.py` decide e monta, `main.registrar_execucao_e_enviar_batimento` registra cada captura completa em `execucoes` e manda o resumo na primeira captura de segunda a partir das 05h de Brasília. O controle de envio fica na tabela `metadados` do banco.
- **`itens_edital`** é tabela filha de `editais` (chave composta `numero_controle_pncp` + `numero_item`, upsert). Documentos/anexos do edital **não são salvos em lugar nenhum**, busca sempre ao vivo na API do PNCP quando o card é aberto no painel (decisão explícita do Bruno, pra não criar schema novo só pra um link de download).
- Endpoints de itens e de arquivos do PNCP (`/v1/orgaos/{cnpj}/compras/{ano}/{sequencial}/itens` e `.../arquivos`) **não estão documentados no Swagger oficial** (`https://pncp.gov.br/api/consulta/v3/api-docs`), só existem testando contra a API de verdade. Não assumir que outro endpoint parecido existe sem testar. Testar a URL sem o sufixo `/itens` ou `/arquivos` não representa o comportamento real do código (aconteceu de verdade: um 301 nesse endpoint sem sufixo levou a um diagnóstico errado de que `pncp_client.py` estava quebrado, quando as URLs reais com sufixo continuavam funcionando). Validar sempre contra a URL exata que `pncp_client.py` monta, nunca uma variação parecida.
- `scripts/` guarda ferramentas auxiliares rodadas sob demanda (backfill, ressincronização, `reprocessar_itens_truncados.py`), nunca fazem parte do fluxo diário automatizado. Os scripts do fluxo diário (restaurar e publicar o banco) ficam em `.github/scripts/`.
- **Busca de itens (`pncp_client.buscar_itens_da_compra`) pagina de verdade**: o endpoint de itens, sem parâmetros, devolve só 10 itens (isso cortou 350 editais do banco em 10 itens). Agora pede 500 por página e só para quando a página vem vazia ou 204, **nunca** por "página menor que o pedido" (o máximo real do endpoint não é documentado). Falha em qualquer página devolve `None`, nunca lista parcial. `_fazer_requisicao` respeita `Retry-After` em 429/503 (teto de 60 s).

## Riscos aceitos, não mitigados

Riscos externos, fora do nosso código, que já avaliamos e decidimos não tentar corrigir por enquanto (custo/complexidade da mitigação maior que o benefício, ou fora do nosso controle). Registrados aqui pra não reabrir a mesma discussão do zero cada vez que acontecem de novo.

- **PNCP responde 429/500/timeout de forma persistente, esgotando as tentativas.** `pncp_client.py` já tenta de novo automaticamente num erro de rede, mas em dias de instabilidade maior do PNCP, um município pode esgotar todas as tentativas e ficar de fora de uma execução específica (fica registrado no log e num resumo ao final da captura, ver `main.capturar_editais`). Aceito como risco do lado do PNCP: o mesmo edital continua aberto e é pego na próxima execução agendada (7h/13h), então o impacto é só um atraso pontual, não perda de dado.
- **Painel do Streamlit Community Cloud hiberna por inatividade.** No plano gratuito, um app sem visita por um tempo hiberna, e a próxima pessoa a abrir o link precisa esperar ele "acordar" (ou clicar num botão). Relacionado à pendência já registrada de o painel servir uso comercial da NexLicit num plano pensado pra uso pessoal/não comercial (ver memória `pendencia-uso-comercial-community-cloud`). Sem ação prevista por ora; resolver isso é a mesma decisão de migrar de hospedagem, ainda não tomada.
- **GitHub Actions pode falhar por infraestrutura do próprio GitHub, antes mesmo do job começar.** Aconteceu pela primeira vez em 06/08/2026 (run #41, `captura-diaria.yml`): o job nunca chegou a ter um runner alocado (nenhum step rodou), erro "The job was not acquired by Runner of type hosted even after multiple attempts". Confirmado via githubstatus.com que foi um incidente oficial do GitHub ("Incident with Actions", impacto "critical", 15:22 as 00:05 UTC), não falha do nosso código, primeira ocorrência em 42 execuções do workflow. Decisão: não construir retry automático (não existe mecanismo nativo do GitHub Actions pra isso, e um workflow de retry caseiro rodaria na mesma infraestrutura degradada, sem garantia de funcionar durante um incidente desse porte). A agenda dupla (7h/13h) já dá redundância natural, e a branch `data` mantém o último banco bom enquanto isso. O aviso por e-mail de falha é nativo do GitHub (Settings > Notifications > Actions), não depende de nada no nosso repositório.

## Lições aprendidas com o Streamlit

- `st.container(key="algo")` gera a classe CSS `st-key-algo`, documentada e estável entre versões. CSS mirando isso é seguro. CSS mirando classe interna automática do Streamlit é frágil, evitar.
- `gap=None` num container tira o espaçamento automático entre os elementos dele: sem isso, o espaçamento "some" era o padrão do Streamlit (16px/"small") somado a qualquer margem própria escrita a mão, o que gerava inconsistência difícil de prever. Preferir `gap=None` + margem explícita quando o espaçamento precisa ser controlado com precisão.
- `st.expander` por padrão executa o conteúdo mesmo fechado. Pra carregamento preguiçoso de verdade (só busca dado quando o usuário abre), precisa de `on_change="rerun"` e checar a propriedade `.open` antes de fazer a busca.
- `AppTest` (ferramenta de teste automatizado do próprio Streamlit) não consegue simular abrir um expander com `on_change="rerun"`, nem tem um jeito nativo de verificar clique num `st.link_button`. Testar essas duas peças isoladas (chamando a função de renderização direto) dá confiança razoável, mas a confirmação final desses fluxos específicos depende de teste manual real.
- Depois de editar um módulo importado pelo `painel/app.py` (ex. `captura/banco.py`), **um processo `streamlit run` já rodando não pega a mudança sozinho**: o Streamlit re-executa o script principal a cada hot-reload, mas não reimporta módulos já carregados no mesmo processo Python. Sempre matar o processo antigo (`netstat -ano | grep :8501` pra achar o PID, `taskkill //F //PID <pid>`) antes de subir um novo depois de mexer em qualquer arquivo fora de `painel/app.py`. O mesmo tipo de cache pode acontecer no Streamlit Community Cloud; a correção lá é um reboot manual pelo "Manage app".
- **Depois de qualquer merge que mude `captura/banco.py` (ou outro módulo importado) e `painel/app.py` ao mesmo tempo, é preciso reiniciar o app no Community Cloud ("Manage app", Reboot app)**, senão ele pode rodar o `app.py` novo com o módulo velho na memória. Aconteceu de verdade em 24/11/2026 (merge `357eef7`): o painel quebrou com `AttributeError: module 'captura.banco' has no attribute 'SITUACAO_DIVULGADA'`. Por isso o `painel/app.py` não depende de constante nova de módulo para comparações simples (tem `SITUACAO_DIVULGADA` própria) e filtra editais excluídos por conta própria além do filtro do banco. Regra para código novo do painel: preferir um valor local a um atributo novo de `captura/*.py` quando a comparação for trivial, e avisar o Bruno do reboot quando não der.
- **`requirements.txt` fixa a versão do `streamlit`, mas isso não trava as dependências transitivas dele** (bibliotecas que o streamlit usa por baixo, tipo `starlette`). Se o streamlit declara uma dependência sem teto máximo (ex. `starlette>=0.40.0`), uma reinstalação do zero (deploy novo, reboot no Community Cloud) pode puxar uma versão bem mais nova dessa dependência, mesmo sem nenhuma mudança nossa no código. Aconteceu de verdade em 05/08/2026: o `starlette` 1.4.0 tornou um parâmetro novo obrigatório numa classe interna (`GZipResponder`), e o `streamlit` (nem a versão mais recente disponível na hora) nunca foi atualizado pra passar esse parâmetro, quebrando o painel público com `TypeError` assim que o Community Cloud reinstalou as dependências do zero. Correção: fixar também a dependência transitiva problemática no `requirements.txt` (com comentário explicando o motivo), removendo a trava só quando o streamlit lançar uma versão corrigida. Vale de exemplo geral: qualquer dependência transitiva sem teto máximo é um risco de quebra silenciosa numa reinstalação futura, não só nesse caso específico do starlette.
- Não existe `runtime.txt` (nem equivalente) neste repositório fixando a versão do Python que o Streamlit Community Cloud usa pra rodar o painel. Quem decide isso é o próprio Streamlit Cloud (escolhido em "Advanced settings" no deploy), e pode mudar sem nenhuma ação nossa. Isso é diferente da versão do Python do workflow "Captura diaria" no GitHub Actions (fixada em `python-version: "3.12"` no `.github/workflows/captura-diaria.yml`), que é um ambiente totalmente separado, usado só pra rodar `main.py`. Não confundir os dois ambientes ao diagnosticar um erro do painel.

## Como rodar localmente

```
python main.py --dias 7                              # captura, sem enviar e-mail
python main.py --dias 7 --enviar-email seu@email.com  # captura + envia e-mail
python main.py --historico --dias 90                  # so consulta o banco local
streamlit run painel/app.py --server.port 8501        # painel local
python -m pytest tests/ -v                             # suite de testes
```
